1. 整理需求与验收条件
请先阅读作业说明，整理 AI Panel Studio 的用户流程和 MVP 范围。把「发起讨论 → 查看阵容 → 确认开场 → 观看发言 → 查看总结」写清楚，再单独描述访客如何加入正在进行的讨论。区分作业明确要求的功能和需要我决定的细节。每项功能给出一个可观察的验收条件，例如「访客进入已有场次后，能看到进入前的发言和之后收到的新发言」。本轮先整理 PRD，等我确认范围后再写代码。

2. 根据需求推荐技术栈
请根据 PRD 推荐一套适合个人完成、可以本地运行的技术栈。分别给出前端、后端、数据库、实时更新和模型接入方案，并说明每项选择解决了什么问题。重点考虑多场讨论隔离、访客中途加入、刷新后继续接收发言，以及自动化测试的可复现性。给出推荐组合和采用理由，等我确认后再按选定方案设计。

3. 把项目拆成多个步骤分别完成
请根据 PRD 和确认后的技术栈，把项目拆成「需求与技术设计 → SQLite 建库 → 后端实现 → 样例导入 → 前端接入 → 自动化测试 → 交付与文档修订」。对每一步写清楚依赖、交付文件和验收方式，并分别给出可执行的 Prompt。一次只推进当前阶段，核对交付文件和验证结果后，再进入下一步。

5. 实现讨论后端
请按 PRD、数据模型和 API 契约实现 FastAPI 后端。创建场次后异步生成阵容，默认 1 位主持人和 4 位专家，用户确认后才开始讨论。模型提供候选发言意向和文本，后端校验候选、决定下一步并保存结果。覆盖无人回应时主持人追问、正式发言控制在 1–2 句、讨论中更新共识与分歧，以及最后生成总结。把讨论结果和公开事件在同一事务里保存，支持按场次查询和 SSE 续接。

三个典型问题与解决路径
1. 页面跳过专家的「准备发言」状态。 Playwright 断言失败后，我让 AI 保留原断言，分别查后端发出的 SSE、浏览器收到的事件顺序和页面显示。事件到达顺序正确，问题出在连续更新被合并渲染。于是把接收游标和显示节奏分开，游标在事件处理后立即推进，专家状态按队列短暂停留再切换。原用例随后复跑通过。
2. 刷新和重连可能漏发言或显示重复。 我让 AI 用一条具体时间线检查详情查询和订阅之间的窗口。后端改用同一个 SQLite 读事务取得快照和对应游标，浏览器从该游标之后接续事件，并按发言 ID 去重。两场并行和刷新用例验证了历史恢复与去重。
3. Playwright 在 Windows 上启动失败。 我把实际报错交给 AI，按前端构建、浏览器启动、业务断言逐层定位。构建恢复后，日志仍显示缺少 Playwright 所需的 Chromium 可执行文件。我改用本机 Chrome，并启用项目已有的 Windows 测试兼容配置。最后 5 项端到端用例全部通过，覆盖阵容确认、访客加入、并行场次、刷新恢复和窄屏操作。
我对工程化 AI 开发的理解
我会先把需求写成可以失败的验收条件，再把实现限制在一个可检查的范围内。AI 可以提出方案、编写实现和复现报错，方案是否采用由我根据代码、运行结果和提交差异判断。这个项目里，固定模型测试验证了应用如何处理已知响应，真实模型的输出质量和时延仍需单独验证。把两种结果分别记录，下一轮才知道该调整模型提示词，还是修复应用逻辑。
